# Зависание трека на одном и том же месте — разбор и фикс

## Симптом

Трек играет, потом на фиксированной позиции останавливается и «вечно грузит».
Перемотка на 1 секунду вперёд возвращает воспроизведение, и дальше трек идёт нормально.
В веб-плеере Navidrome тот же файл играет без заминок.

## Диагноз

Симптом — «зависло на 11.702 с, перемотка на секунду оживляет, в логе ни одной строки
PlayerManager». По этому репро сначала были сняты две рабочие версии, а потом найдена настоящая
причина. Всё измерено, а не предположено:

| Проверка | Результат |
|---|---|
| `m.iswebdev.ru` (Navidrome 0.63.2) отдаёт Range? | `206` + `content-range: bytes 0-0/34264126`, `accept-ranges: bytes` ✅ |
| Range ровно на смещении точки «зависания» (~1.52 МБ) | `206`, тело 1001 байт; 32.7 МБ с этого места за 12.55 с ✅ |
| Полный файл | 34 264 126 байт за 7.9 с (HTTP/1.1) и 9.1 с (h2), без обрывов ✅ |
| Сам файл (`Тараканы! — То, что не убивает тебя.flac`) | эталонный декодер прочитал **11 642 400 кадров** @44.1 кГц — ровно как в метаданных Navidrome; ни одного повторяющегося блока, ни одной тишины >0.33 с; на 11.702 с громкий звук (RMS 12 285) ✅ |
| Буфер в момент «зависания» | при буфере в 50 с загрузчик к 11.7 с ушёл на ~6 МБ вперёд ⇒ дело **не** в нехватке данных ✅ |

Значит: сервер здоров, файл здоров, данных вдоволь. Остаётся состояние самого плеера — и оно
выводится из твоего же лога дедуктивно, без догадок.

### Причина №1 (то, что ты и поймал): очередь перезаписывалась поверх игры, плеер бросался в `STATE_IDLE`

В `PlayerManager.init` стоит `delay(5000)`, после чего `tryRestoreQueueFromServerIfNeeded()` идёт
на сервер за сохранённой очередью (`getPlayQueue`). Пока идёт сетевой запрос (1–6 с), проверка
«локальная очередь пуста» уже пройдена, и пользователь успевает нажать play. Дальше выполняется:

```kotlin
player.setMediaItems(mediaItems, startIndex, position)   // ← плеер уходит в STATE_IDLE
// и, если autoPlay == false, prepare() СОЗНАТЕЛЬНО НЕ ВЫЗЫВАЕТСЯ:
PerformanceTracer.log("restoreQueue", "Skipping prepare() for autoPlay=false - FIX FOR 2-3 MIN LAG!...")
```

`Player.setMediaItems()` **не подготавливает** плеер. В `STATE_IDLE` нет ни загрузки, ни рендера,
при этом `playWhenReady` остаётся `true` (установка очереди его не сбрасывает). Получается картина
из лога, байт в байт:

* позиция не движется и равна **серверной** сохранённой — отсюда «одно и то же место»: 11.702 с —
  это не место в файле, это то, что лежало на сервере в `savePlayQueue`;
* UI врёт: `_playerState.update { isPlaying = autoPlay }` ставит «паузу» у реально игравшего трека;
* **ни одной строки в логе** — и вот почему. Сторож проверял только `STATE_BUFFERING && playWhenReady`
  и `STATE_READY && isPlaying`. Комбинация `playWhenReady == true` при `STATE_IDLE` не попала ни в
  одну ветку; исключений тоже нет → 100 секунд тишины и десяток спасённых `position=11702`.
  Молчание watchdog было слепой зоной детектора, а не признаком того, что всё хорошо;
* **перемотка лечит**: `Player.seekTo()` из `STATE_IDLE` неявно подготавливает плеер — то же самое
  делает и кнопка play (её ветка `if (state == STATE_IDLE) prepare()`), поэтому симптом
  «оживает на секунду» выглядит как чудо, а на деле это просто вызов `prepare()`.

Отдельно: та же функция вызывается кнопкой «синхронизировать очередь» на экране `QueueScreen`
вообще без условий — то есть **нажатие этой кнопки во время воспроизведения раньше гарантированно
глушило музыку**. Это самая быстрая проверка диагноза на устройстве.

Почему веб-плеер не виснет: `<audio>` читает файл одним последовательным соединением и никогда не
переустанавливает плейлист на середине воспроизведения.

### Причина №2 (тоже устранена, но к этому логу отношения не имеет): транспорт и дефолты Media3

Она реальна и на других серверах ломает воспроизведение, поэтому в патче оставлена — но для
`m.iswebdev.ru` и этого трека измерением исключена: Range работает, `skipFully` вызвать нечем,
буфер не успевает опустеть.

### Механизм причины №2

Плеер собирался как `ExoPlayer.Builder(context).build()`, то есть на дефолтах Media3.

**Шаг 1. Дефолт буферизации заставляет плеер пересоздавать HTTP-запрос каждые 50 секунд.**
В `DefaultLoadControl` (проверено по исходникам 1.7.1):

```java
public static final int DEFAULT_MIN_BUFFER_MS = 50_000;
public static final int DEFAULT_MAX_BUFFER_MS = 50_000;
public static final boolean DEFAULT_PRIORITIZE_TIME_OVER_SIZE_THRESHOLDS = false;
```

`shouldContinueLoading()` (строка 402) выключает загрузку, как только буфер достиг
`maxBufferUs`, и включает снова, когда он упал ниже `minBufferUs`. min == max == 50 с, поэтому
на треке длиннее минуты плеер **закрывает соединение и открывает новое с `Range: bytes=<позиция>-`**
снова и снова, десятки раз за песню.

**Шаг 2. Если сервер ответил на Range не `206`, а `200`, плеер обязан «добрать» позицию чтением
впустую.** `DefaultHttpDataSource.open()` (1.7.1, строки 412–455):

```java
// If we requested a range starting from a non-zero position and received a 200 rather than a
// 206, then the server does not support partial requests. We'll need to manually skip to the
// requested position.
long bytesToSkip = responseCode == 200 && dataSpec.position != 0 ? dataSpec.position : 0;
...
skipFully(bytesToSkip, dataSpec);
```

`skipFully()` читает и **выбрасывает** байты буфером по 4096:

```java
byte[] skipBuffer = new byte[4096];
while (bytesToSkip > 0) {
    int readLength = (int) min(bytesToSkip, skipBuffer.length);
    int read = inputStream.read(skipBuffer, 0, readLength);
```

Середина 3-минутного 320 kbps трека — это порядка 4 МБ, то есть ~1000 итераций `read()`.
Звук стоит, `playbackState == STATE_BUFFERING`, исключения нет. Отсюда «завис и не грузится».
Недостаточно просто подождать: как только `Loader` уходит в retry и получает `read == -1`,
прилетает `ERROR_CODE_IO_READ_POSITION_OUT_OF_RANGE`.

Та же логика есть в `OkHttpDataSource` (строки 324/338) — то есть **переход на OkHttp-источник
сам по себе ничего не чинит**, я это проверил, чтобы не предлагать ложное решение.

**Шаг 3. Что переводит сервер в режим «без Range» (проверено на живом сервере):**

```
GET /rest/stream.view?id=...                      -> HTTP 206, accept-ranges: bytes   ✅
GET /rest/stream.view?id=...&format=flac          -> HTTP 200, accept-ranges: none,   ❌
                                                     без Content-Length (chunked)
```

Как только ответ попадает во вторую колонку, перезапрос куска невозможен физически.
Именно это и происходило в твоём приложении дважды:

* **`&format=raw`** в `retryCurrentTrackWithFreshUrl()`. Такого значения `format` в Subsonic API
  нет. Navidrome его игнорирует (проверено: `format=raw` всё ещё отдаёт 206), но для большинства
  других реализаций «неизвестный формат» = «сделай транскод» = `accept-ranges: none`.
  То есть **первая же попытка восстановления переводила поток в режим, из которого выбраться
  нельзя** — «дальше никак не хочет грузиться» создавалось руками приложения.
* прокси/CDN перед сервером, которые режут `Range` или сжимают `audio/*` в gzip
  (тогда `Content-Length` относится к сжатому телу — см. `isCompressed`-ветку там же в `open()`).

**Шаг 4. Таймауты.** `DefaultHttpDataSource` по умолчанию — `8 000 мс` на connect и **на read**:

```java
public static final int DEFAULT_CONNECT_TIMEOUT_MILLIS = 8 * 1000;
public static final int DEFAULT_READ_TIMEOUT_MILLIS = 8 * 1000;
```

при том, что API-клиент этого же приложения (`NetworkModule`) использует 30 с. Медленная, но
штатная дозагрузка на мобильной сети укладывалась в 8 с и превращалась в ошибку.

### Почему «костыли» ухудшали картину

В `PlayerManager` на этот симптом было навешано три реакции, и каждая добавляла проблему:

| Было | Что ломало |
|---|---|
| `skipCorruptedSegment()` — seek на `+3.5 с` | молча срезал 3.5 с музыки; «битого» места в файле нет |
| повтор с `&format=raw` | загонял поток в не-rangeable режим, после чего трек не грузился уже никогда |
| `setMediaItem() + prepare()` | выбрасывал уже скачанный буфер, трек грузился с нуля |
| `bufferingTimeoutMs = 15 с → handlePlayerError(null)` | легитимный медленный старт считался ошибкой и запускал каскад перезапусков |

## Что сделано

### 1. `player/PlaybackEngine.kt` (новый, Hilt `@Singleton`)

Единое место настройки медиа-обвязки, общая для основного и кроссфейдного плееров:

* **`DefaultLoadControl`** — `minBuffer 45 с / maxBuffer 180 с`,
  `prioritizeTimeOverSizeThresholds(true)`, старт через 1.5 с, после ребаффера 3 с.
  Зазор min/max и большой max убирают сам цикл «стоп → Range-перезапрос»: трек читается
  одним непрерывным соединением, `skipFully` вызвать нечем.
* **`SimpleCache` + `CacheDataSource`** — скачанное ложится на диск
  (`noBackupFilesDir/audio_cache`, LRU, 150 МБ, `FLAG_IGNORE_CACHE_ON_ERROR`).
  Любая дозагрузка и перемотка внутри уже скачанного читают с диска, а не из сети.
  Кэш лежит не в `cacheDir`, потому что Android имеет право вычистить `cacheDir` в любой момент.
* **`DefaultHttpDataSource`** с явными таймаутами (connect 15 с / read 30 с — как у API-клиента),
  `setAllowCrossProtocolRedirects(true)` и `Accept-Encoding: identity`
  (защита от gzip-прокси, ломающего `Content-Length`).
* **Стабильный ключ кэша.** Дефолт Media3 — полный URI, а в нём `u`/`t`/`s` (логин/токен/соль):
  после перевхода тот же файл качался бы заново, а старое копировалось в кэш.
  Ключ строится из `host + path` и только значимых query-параметров (`id`, `format`, `maxBitRate`…),
  авторизационные отбрасываются.

### 2. `player/PlayerManager.kt`

* Оба `ExoPlayer.Builder` (основной и кроссфейдный) получают `createMediaSourceFactory()`
  и `createLoadControl()`.
* Удалены `skipCorruptedSegment()`, `&format=raw`, повтор через `setMediaItem()+prepare()`.
* Сторож оставлен, но делает ровно одно безопасное действие: `recoverStalledPlayback()` —
  `seekTo(текущая позиция)`. Это отменяет зависшую загрузку и запускает новую, сохраняя
  `MediaItem`, очередь и скачанные байты — то же самое, что ты делаешь руками, только без
  потери секунды звука. После `maxStallRecoveries = 2` неудач — переход к следующему треку.
* Исправлено поведение сторожа: раньше при таймауте `bufferingStartTime` обнулялся, из-за чего
  восстановление вызывалось почти каждый тик. Теперь отсчёт сдвигается, попытки редкие.
* Убрано проглатывание `CancellationException` в восстановлении.

### 2b. `restoreQueueFromServer()` больше не глушит живое воспроизведение (причина №1)

* `tryRestoreQueueFromServerIfNeeded()` перепроверяет «идёт ли локально музыка» **после** сетевого
  `getPlayQueue()`, а не только до — это и закрывало гонку «нажал play, пока шёл запрос».
* При активном локальном воспроизведении `restoreQueueFromServer()` сохраняет **текущий** трек и
  **текущую** позицию вместо серверных и обязательно вызывает `prepare()`, если аудио шло либо
  плеер был подготовлен. Отложенный `prepare()` сохранён ровно там, где и задумывалась экономия:
  «очередь восстановили, когда ничего не играло».
* `_playerState.isPlaying` больше не пишется константой `autoPlay` — берётся реальное
  `player.isPlaying`, чтобы UI не показывал паузу у играющего трека.
* Добавлен `userWantsPlayback` — явное намерение слушателя (`true` на старте/возобновлении,
  `false` на пользовательской паузе и на срабатывании sleep-таймера). По нему сторож отличает
  «пользователь сам поставил паузу» от «музыку заглушили изнутри».

### 2c. Сторож: слепая зона закрыта

* Критерий один: **«звук нужен, а позиция не движется»**, независимо от `playbackState`. Прежние
  ветки требовали конкретных состояний, и `STATE_IDLE` при `playWhenReady == true` был невидим.
* Пороги разделены: при `pos == 0` (ещё не начиналось — медленный старт по мобильной сети нормален)
  ждём 20 с; если же шла позиция и встала — 10 с. Без этого разделения восстановление само бы
  разгоняло цикл бесконечных перезагрузок.
* В `recoverStalledPlayback()` добавлен явный выход из `STATE_IDLE` через `prepare()`. `seekTo`
  неявно готовит плеер, но полагаться на неявное в коде лечения зависаний нельзя.
* Каждое срабатывание пишет полный кортеж: `state`, `isPlaying`, `buffered`, `suppression`, `error`,
  `song` — чтобы следующий разбор не начинался с угадывания.
* `setAudioAttributes(USAGE_MEDIA / CONTENT_TYPE_MUSIC)` на обоих плеерах: раньше `setAudioAttributes`
  не вызывался нигде, и плеер наследовал `AudioAttributes.DEFAULT` (`USAGE_UNKNOWN`) — ОС не считает
  поток музыкой (маршрутизация, поведение при звонке). `handleAudioFocus` явно оставлен `false`:
  включённый автофокус сам по себе вешает паузы при фокус-потерях, а паузы мы здесь и ловили.

### 3. `SonicSpotApp.kt`

Прогрев `SimpleCache` (создание папки + открытие SQLite-индекса) на `Dispatchers.IO` в
`onCreate()` — по образцу уже имеющегося прогрева Coil, чтобы первый старт трека не платил
за это на главном потоке.

### 4. `app/build.gradle.kts`

Явно добавлено `media3-datasource`, `media3-database`, `annotation-experimental`
(все три и так приходили транзитивно от `media3-exoplayer`/Compose — теперь они заявлены,
потому что импортируются напрямую). **Новых библиотек в APK нет.**

## Что важно: `RetryDataSourceFactory` в Media3 нет

В ExoPlayer 2.x был `RetryDataSourceFactory` — «правильный» ответ на такие зависания.
В Media3 1.7.1 его **вырезали** (проверено по дереву тегов androidx/media@1.7.1), поэтому
устойчивость собрана из кэша, буферизации и одного аккуратного восстановления.

## Третий раунд: причина найдена — Bluetooth и `AUDIO_BECOMING_NOISY`

Три факта сняли неопределённость: сборка **новая**, звук идёт на **Bluetooth-гарнитуру**, кнопка
в плеере **дёргается** (то «играет», то «остановлено»), музыка при этом не продолжается.

Дёрганье кнопки — это `isPlaying`, то есть `playWhenReady` кто-то переключает туда-обратно.
И такой переключатель в коде ровно один:

```kotlin
.setHandleAudioBecomingNoisy(true)   // основной плеер
```

Что делает Media3 внутри — `ExoPlayerImpl.onAudioBecomingNoisy()` (1.7.1, строка 3184), целиком:

```java
@Override
public void onAudioBecomingNoisy() {
  updatePlayWhenReady(
      /* playWhenReady= */ false, Player.PLAY_WHEN_READY_CHANGE_REASON_AUDIO_BECOMING_NOISY);
}
```

`ACTION_AUDIO_BECOMING_NOISY` прилетает при **любом** событии гарнитуры: переподключение, смена
дорожки, пересогласование кодека A2DP, да просто фантомные события на части устройств. Результат —
то, что и было в логе:

* музыка останавливается, но **исключения нет** — `handlePlayerError` не вызывается;
* `playWhenReady == false`, позиция замирает;
* сторож (и прежний, и мой) молчит, потому что ждёт либо `STATE_BUFFERING`, либо `STATE_READY`;
* пользователь видит «паузу» и жмёт play — отсюда дёрганье кнопки;
* **перемотка «лечит»**: `seekTo()` из этого состояния поднимает `playWhenReady` обратно.

Почему веб-плеер не виснет: браузер не подписан на `ACTION_AUDIO_BECOMING_NOISY`.

### Исправление

* `.setHandleAudioBecomingNoisy(false)` на основном плеере — убирает сам источник самопроизвольных
  остановок. Кроссфейдный плеер в этом же файле всегда так и создавался.
* Если `playWhenReady` всё же снят **не пользователем**, сторож поднимает его через **1.5 с**
  (а не через 10 с, как при нехватке данных): снятая готовность играть при живом намерении
  слушать — это немедленная неисправность, а не медленная сеть.
* Причина каждой остановки пишется в лог: `USER_REQUEST`, `AUDIO_FOCUS_LOSS`,
  `AUDIO_BECOMING_NOISY`, `REMOTE`, `END_OF_MEDIA_ITEM`, `SUPPRESSED_TOO_LONG`.
  Намерение слушать снимает только `USER_REQUEST`.

Если станет важным останавливать музыку при вынимании наушников — верни `true`; причина будет
видна в логе, а не угадываться.

## Четвёртый раунд: хартбит показал истину — и вскрыл баг в моём же восстановлении

С инструментарием лог впервые стал содержательным:

```
heartbeat: pos=11702 dur=264000 state=3 isPlaying=true playWhenReady=true
           wantPlayback=true buffered=106893 song=sl0DWNC2H6b8F5uNbSORJL
state=BUFFERING playWhenReady=true pos=11702 ...
AudioTrack: getTimestamp_l(5276): device stall time corrected
state=READY    playWhenReady=true pos=11702 ...
state=BUFFERING playWhenReady=true pos=11702 ...   ← каждые ~150 мс
state=READY    playWhenReady=true pos=11702 ...
```

Читается однозначно:

* `state=3` — READY, `playWhenReady=true`, `isPlaying=true` — плеер считает, что играет;
* `buffered=106893` при `pos=11702` — **данных на 95 секунд вперёд**;
* позиция стоит на месте;
* состояние дёргается BUFFERING↔READY ~7 раз в секунду — это и есть «дёргается кнопка паузы».

Вывод: скачивать нечего и не нужно, дело в **тракте вывода** — AudioTrack не забирает уже
скачанное. BT-правка сработала (`playWhenReady` больше не снимается), проблема ушла уровнем ниже.

### Попутно нашёлся баг в моём же восстановлении

Успех проверялся так:

```kotlin
delay(6_000)
if (state == Player.STATE_READY) { stallRecoveryAttempts = 0 }
```

При дёргающемся состоянии через 6 с мы с ~50 % вероятностью ловим `READY`, обнуляем счётчик — и
**лестница никогда не поднималась выше первой ступени**, то есть выше `seekTo`. А `seekTo` не может
вылечить тракт, который не ест 95 скачанных секунд: качать-то нечего.

### Что исправлено

* **Успех определяется по позиции, а не по состоянию**: `recovered = newPos > pos + 800L`.
  Состояние при залипшем тракте врать не может перестать, а позиция — нет.
* **Причина определяет первую ступень.** `SINK_STALL` (данные есть, звук не идёт) больше не
  тратит попытку на бесполезный `seekTo`, а сразу перезапускает тракт:
  1. `pause()` + `play()` — `audioTrack.pause()/play()`;
  2. `stop()` + `prepare()` + `seekTo()` + `play()` — полное пересоздание AudioTrack и рендерера.
  Для `NO_DATA` (реально нет данных) первая ступень по-прежнему щадящая — перезапуск загрузки.
* **Лестница прогоняется за один заход** с паузой 3 с между ступенями вместо полного цикла
  детекции 10 с: до пересоздания тракта проходило больше полминуты тишины, теперь ~13 с.
* **Убран старый предохранитель** «счётчик >= лимита → сразу следующий трек». Он читал унаследованное
  значение от прерванной попытки и мог отправить на следующий трек вообще без попыток лечения.
  Теперь лестница ограничена сама, а счётчик всегда обнуляется в конце.

## Пятый раунд: механизм залипания выведен до строки кода

Лог 23:35 дал недостающее звено — трек реально **играл ~7 секунд** и только потом встал:

```
23:35:31.032  playWhenReady=true (USER_REQUEST) pos=4991   ← пользователь нажал play
23:35:38.124  heartbeat: pos=11702 buffered=115043         ← доиграло за 7 с до 11702
23:35:40.6+   state=BUFFERING↔READY, pos=11702             ← встало, данных на 103 с вперёд
```

Задержка в ~7 с — не случайность, и `buffered` снова ушёл на 103 с вперёд. Складывается
полная цепочка, подтверждённая исходниками Media3 1.7.1.

### Почему позиция замирает

`AudioTrackPositionTracker.getCurrentPositionUs()` (строка 287):

```java
boolean useGetTimestampMode = audioTimestampPoller.hasAdvancingTimestamp();
if (useGetTimestampMode) {
    long timestampPositionUs = sampleCountToDurationUs(audioTimestampPoller.getTimestampPositionFrames(), outputSampleRate);
    long elapsedSinceTimestampUs = systemTimeUs - audioTimestampPoller.getTimestampSystemTimeUs();
    positionUs = timestampPositionUs + elapsedSinceTimestampUs;
} else {
    positionUs = systemTimeUs + smoothedPlayheadOffsetUs;   // по playback head — работает
}
```

В режиме таймстемпа позиция = «кадры из метки» + «сколько времени прошло с момента метки».
Когда устройство залипает, Android **подменяет время метки на текущее** — это ровно сообщение из
лога: `getTimestamp_l: device stall time corrected using current time`. Тогда
`elapsedSinceTimestampUs ≈ 0`, и `positionUs` замирает на значении `timestampPositionUs`.

### Почему само не рассасывается

`AudioTimestampPoller.maybePollTimestamp()` (строка 157) покидает `STATE_TIMESTAMP_ADVANCING`
только когда `getTimestamp()` **вернул ошибку**:

```java
case STATE_TIMESTAMP_ADVANCING:
    if (!updatedTimestamp) { reset(); }   // только при ОШИБКЕ получения метки
    break;
```

А в нашем случае `getTimestamp()` **успешен** — система отдаёт метку, просто с подменённым
временем. Значит `updatedTimestamp == true`, поллер остаётся в `STATE_TIMESTAMP_ADVANCING`
навсегда, и позиция стоит вечно. Этим же объясняются ~7 с нормального звука: сразу после старта
поллер в `STATE_INITIALIZING` и считает позицию по playback head; как только метка «поехала», он
переходит в опасный режим — и замирает при первом же залипании устройства.

### Почему помогает перемотка

`DefaultAudioSink.flush()` (строка 1549):

```java
public void flush() {
  if (isAudioTrackInitialized()) {
    resetSinkStateForFlush();
    ...
    audioTrackPositionTracker.reset();     // ← поллер снова в INITIALIZING
    // We need to release the audio track on every flush because of known issues on some devices
```

То есть `flush()` сбрасывает трекер позиции **и пересоздаёт AudioTrack**. Поллер возвращается в
`INITIALIZING`, снова считает позицию по playback head — звук идёт. Это ровно то, что ты делал
руками перемоткой на секунду.

### Что сделано

Первая ступень для `SINK_STALL` — принудительный сброс, повторяющий проверенный ручной приём:

```kotlin
private fun flushSinkByNudge(player: Player, pos: Long) {
    player.seekTo(pos + 250L)   // смена позиции гарантирует discontinuity и flush()
    player.playWhenReady = true
}
```

Сдвиг на 250 мс, а не `seekTo` на ту же позицию: смена позиции гарантирует настоящий
discontinuity и, как следствие, вызов `flush()`. Стоит это четверть секунды звука вместо
зависания. Лестница целиком: `flushSinkByNudge` → `pause/play` → `stop+prepare+seek+play`.

## Шестой раунд: проверка файла, отклонённая собственная гипотеза и уточнение механизма

### Гипотеза «в файле есть кадр, на котором спотыкается кодек» — проверена и ОТВЕРГНУТА

Соблазн был большой: трек вставал на одной и той же позиции (11702 мс) в трёх сессиях подряд.
Первый замер показал аномалию — кадры 112–113 (11.703 с и 11.807 с) имели размер 6141 и 7443 байта
при медиане 13 830. Это ровно там, где замирает воспроизведение.

Проверил строже — и гипотеза рассыпалась. Признак «маленький кадр» оказался артефактом: в список
кадров попадали ложные срабатывания CRC-8 (из 4041 кандидатов валидными казались 2532, хотя кадров
должно быть 2526). Отфильтровал по **последовательности номеров кадров** (при `blocking=0` номер
кадра во FLAC идёт +1), получилось ровно 2526 — и картина вокруг точки зависания стала обычной:

```
кадр 111  время=11.598с  размер=13701
кадр 112  время=11.703с  размер=13584   ← было «6141» из-за ложного кадра
кадр 113  время=11.807с  размер=13333   ← было «7443»
```

Ни смены конфигурации потока, ни аномальных размеров. В сочетании с полным эталонным декодированием
(11 642 400 кадров без единой ошибки) файл признан здоровым, и версия «кодек спотыкается на данных»
закрыта.

### Как на самом деле замирает позиция

`DefaultAudioSink.getCurrentPositionUs()` обрезает позицию по **записанному** объёму:

```java
positionUs = min(positionUs, configuration.framesToDurationUs(getWrittenFrames()));
```

Поэтому позиция встаёт не там, где «кончились данные», а там, где **трек перестал забирать
записанное**. Это согласуется со всем: `buffered` ушёл далеко вперёд (скачано), а `pos` стоит на
объёме, который успели записать в AudioTrack. Дальше — заминка устройства
(`device stall time corrected`), потому что писать больше некуда.

### Идея «увеличить буфер AudioTrack» — отклонена

`DefaultRenderersFactory.buildAudioSink()` — штатная protected-точка расширения, и
`AudioTrackBufferSizeProvider` существует. Но дефолтный
`DefaultAudioTrackBufferSizeProvider` уже применяет `PCM_BUFFER_MULTIPLICATION_FACTOR = 4`.
Городить нестабильный API ради спекулятивного множителя без возможности проверить — не стоит.

### Что сделано

* **Порог срабатывания зависит от запаса данных.** Когда `buffered - pos > 2 с`, позиция стоит не
  из-за сети и не из-за медленного старта — это однозначно сломанный тракт вывода, и ложного
  срабатывания бояться нечего. В этом случае ждём **5 с**, а не 10. Медленный старт (`pos == 0`)
  по-прежнему 20 с, нехватка данных — 10 с.

### Подозреваемый, которого стоит проверить в первую очередь: кроссфейд

В логе 23:50 зависание наступило вскоре после перехода между треками. Кроссфейд в этом приложении
держит **второй ExoPlayer со своим AudioTrack**, и на Bluetooth одновременно живут два трека.
Проверка дешёвая: переключатель «Плавный переход между треками» лежит в «Настройках»
(`SettingsScreen.kt`, строка 91). Выключи его и послушай — если зависания исчезнут, причина именно
в наложении двух треков на BT, и лечить надо там (например, не держать второй плеер живым после
перехода).

## Второй раунд: что дал повторный лог

Новый лог тот же: `position=11702` стоит ~46 с, `AudioTrack ... device stall time corrected`,
декодер при этом **работает** (`BufferPoolAccessor` нарастил `alloc` с 1159 до 2135 за 10 с —
это заметно быстрее реального времени, то есть данные гонятся в буфер), но строки `PlayerManager`
нет вообще.

Отсюда два вывода.

**1. Гипотеза «залип AudioTrack» отпала — проверкой по исходникам Media3.**
`AudioTrackPositionTracker.getCurrentPositionUs()` (1.7.1, строка 287) считает позицию так:

```java
if (useGetTimestampMode) {           // audioTimestampPoller.hasAdvancingTimestamp()
    positionUs = timestampPositionUs + elapsedSinceTimestampUs;   // от настенных часов
} else {
    positionUs = systemTimeUs + smoothedPlayheadOffsetUs;         // тоже от настенных часов
}
```

В **обоих** режимах позиция ведётся от `systemTimeUs`. Значит при залипшем устройстве позиция
уезжала бы *вперёд* (звук пропал, секундомер идёт), а не замирала. Замершая позиция при работающем
декодере так не объясняется.

**2. Найдена слепая зона в моём же стороже.**
Условие было `userWantsPlayback && playWhenReady`. Если что-то сняло `playWhenReady` **за спиной
пользователя** — `AUDIO_BECOMING_NOISY` при отключении Bluetooth, команда MediaSession, потеря
фокуса, переустановка очереди — намерение слушать остаётся, а `playWhenReady == false`, и сторож
молчит. Это ровно то, что видно в логе: тишина, позиция стоит, никаких событий.

Что сделано во втором раунде:

* **Порог срабатывания — намерение пользователя, без `playWhenReady`.** Молчание сторожа больше
  невозможно по построению.
* **`onPlayWhenReadyChanged(playWhenReady, reason)` логируется с причиной**: `USER_REQUEST`,
  `AUDIO_FOCUS_LOSS`, `AUDIO_BECOMING_NOISY`, `REMOTE`, `END_OF_MEDIA_ITEM`,
  `SUPPRESSED_TOO_LONG`. Намерение снимает только `USER_REQUEST` — отказ по «шуму» или внешней
  команде его не снимает, потому что пользователь-то слушать хочет.
* **`onPlaybackStateChanged`** пишет `IDLE/BUFFERING/READY/ENDED` с позицией.
* **Хартбит раз в 10 с** (`heartbeat: pos=... buffered=... state=... playWhenReady=... wantPlayback=...`).
  Он живёт в цикле прогресса, который работает всегда — поэтому лог теперь информативен **даже
  когда ничего не происходит**.
* **Классификация причины при срабатывании.** Главный водораздел — `buffered - pos`:
  * `+>2 с` → `SINK_STALL` — данные скачаны вперёд, но не проигрываются (тракт вывода);
  * иначе → `NO_DATA` — реально не хватает данных (сеть/буфер);
  * отдельно ловятся `PLAY_WHEN_READY_FALSE`, `IDLE`, `ENDED`.
* **Лестница восстановления** вместо одного приёма (лимит поднят до 3):
  1. `prepare()` при `STATE_IDLE` + `seekTo(pos)` + `playWhenReady = true` — перезапуск загрузки,
     буфер сохранён;
  2. `pause()` + `play()` — перезапуск звукового тракта, буфер сохранён;
  3. `stop()` + `prepare()` + `seekTo(pos)` + `play()` — полное пересоздание трека и рендерера.
     Дорого, но благодаря дисковому кэшу `PlaybackEngine` данные перекачивать не нужно.

## Как проверялся код в этой среде (сборки тут нет)

Android SDK/JDK 17 в моей среде нет, поэтому вместо «собрал и посмотрел» сделано следующее:

1. **Синтаксис проверен настоящим компилятором Kotlin 2.0.21**, а не подсчётом скобок:
   `kotlinc` разобрал все три изменённых файла → **0 ошибок вида `expecting`/`unexpected`**.
   Остальные 719 diagnostics — это `unresolved reference` на `android.*`, Hilt и media3:
   их просто нет в classpath (иначе это была бы уже сборка).
2. **Типы всех новых выражений проверены отдельным probe-файлом** против настоящих

   `p.bufferedPosition`, `AudioAttributes.Builder().setUsage(C.USAGE_MEDIA)`,
   `setAudioAttributes(attrs, false)`, `DefaultLoadControl.Builder().setBufferDurationsMs(...)`) →
   **компилируется с exit 0, 0 ошибок**.
3. Сторонние символы сверены через `javap` по байткоду 1.7.1 (см. предыдущий раздел).

Гарантировать успешную сборку это не может (не видны R8, Compose, генерация Hilt), но «не
скомпилируется» из-за опечатки или неверной сигнатуры здесь исключено.

## Как проверить на устройстве

```bash
adb logcat -s PlayerManager:* PlaybackEngine:* DefaultLoadControl:*
```

Ожидается:

* зависаний на середине трека нет;
* **проверка причины №1** (детерминированная, 5 секунд): во время воспроизведения открой «Очередь» и
  нажми кнопку синхронизации. На старом коде музыка глохла сразу и позиция вставала; на новом
  воспроизведение продолжается;
* при любом «не едет» теперь обязана появиться строка
  `Playback not advancing at N ms: state=... buffered=... suppression=... error=...` — молчания у
  сторожа больше нет как варианта, он следит за позицией, а не за состоянием плеера;
* **в норме** в логе вообще нет строк `Recovering stall` — сторона приложения больше
  ничего не «чинит»;
* если что-то всё-таки подвисает, видно `Recovering stall (position stuck at N) — attempt 1/2`
  и воспроизведение продолжается **на той же позиции**, без вырезанных 3.5 с;
* не должно быть `Skipping corrupted segment`, `Trying raw format` — эти строки принадлежат
  удалённым костылям, их появление означает, что собрался старый код.

Если зависание осталось — одной командой проверяем, виноват ли сервер в missing Range:

```bash
curl -sI -H 'Range: bytes=2000000-' \
  'https://SERVER/rest/stream.view?id=ID&u=USER&t=TOKEN&s=SALT&v=1.16.1&c=Spotidrome&f=json' \
  | grep -iE 'HTTP/|accept-ranges|content-length|content-range|content-encoding'
```

Хороший ответ: `206`, `accept-ranges: bytes`, есть `content-range`.
Плохой (200 / `accept-ranges: none` / `content-encoding: gzip`) — значит Range режет прокси или
сервер всегда отдаёт через транскод; лечение тогда на его стороне (для nginx: не трогать
`Accept-Ranges`/`Range`, не включать `gzip_types` для `audio/*`).

## Настройки, которые могут понадобиться

В `PlaybackEngine`:

* `MAX_CACHE_BYTES` — 150 МБ. 150 МБ ≈ 70–100 треков; меньше — если жалко места.
* `MAX_BUFFER_MS` / `MIN_BUFFER_MS` — 180 с / 45 с. Для FLAC 1411 kbps 180 с ≈ 32 МБ в очереди;
  на слабом устройстве можно 90 000/30 000 — защита от `skipFully` останется за счёт кэша.
* `READ_TIMEOUT_MS` — 30 с. Если сервер честно транскодит на лету, увеличь до 60 000.

Не сделано (осознанно, чтобы не расширять патч): экран «Память» пока не показывает и не чистит
`audio_cache`. API для этого в `PlaybackEngine` уже есть — `audioCacheSizeBytes()` и
`clearAudioCache()` — остаётся подключиться в `CacheManager`/`MemoryScreen` по одному вызову.
